## 학습 데이터 구성과 품질 검증

|개념|한 줄 요약|
|---|---|
|모범답안 생성|학습시킬 "정답"은 모델이 아니라 규칙으로 만들어서 일관되게 한다|
|대화 형식과 정답 토큰|손실은 정답(assistant) 토큰에서만 계산하므로, 토큰 단위로 그 경계를 찾는다|
|품질 검사|가중치를 바꾸기 전에 자료부터 검사하고, 검사 함수 자체도 시험한다|

### 근거를 모범답안으로 바꾸기
- SFT 데이터는 "입력 하나+모범답안 하나"의 묶음. 모범답안이 틀리면 틀린 행동을 그대로 학습
- 그래서 모범답안은 모델이 쓴 답을 복사하지 않고 규칙 함수로 만듬. 그래야 틀린 답을 학습시키는 사고를 막을 수 있음.
- 데이터를 모으기 전에 "틀리기 쉬운 경우"를 표로 먼저 설계. 같은 질문인데 문서만 다른 쌍을 일부러 넣는 것이 핵심.

문장 틀이 하나인것의 장점, 한계  
장점 : 형식과 규칙이 흔들리지 않아 "JSON, 보류, 인용"이라는 행동을 확실히 가르칠 수 있다는 것  
한계 : 표현이 다양한 실제 입력에서 일반화되는지 이 데이터만으로는 알 수 없음.  

### 대화 형식과 정답 토큰 구성하기
레코드는 바깥(메타데이터)과 안쪽(messages)으로 나뉨
- 한 줄의 레코드는 메타데이터(id, group_id, case_type) + messages(system, user, assistant)
- 메타데이터는 분리와 분석용이라 모델 입력에 넣지 않음. case_type='over_limit'을 입력에 넣으면 "초과니까 승인"이라는 정답을 알려 주는 셈이라 정답 누수임.
- massages 형식은 Oppen AI Chat, HF 채팅 템플릿, TRL SFTTrainer가 그대로 받는 사실상 표준. [{"role": ..., "content": ...}, ...]

|언제|넣는 messages|이유|
|---|---|---|
|학습|system+user+assistant|assistant(모범답안) 토큰에서 손실 계산|
|생성/평가|system+user|정답을 넣으면 평가가 무의미|

SFT는 정답(assistant) 토큰에서만 손실을 계산함. 그러려면 전체 토큰 중 어디부터가 정답인지 알아야 함. 그래서 같은 대화를 두 번 토큰화함.
- prompt_ids : 정답 없는 대화(system + user), add_generation_prompt=True -> 끝에 assistant 시작 표시
- full_ids : 정답 있는 전체 대화, add_generation_prompt=False -> 정답이 이미 있으므로
- full_ids[:len(prompt_ids)] == prompt_ids를 assert로 확인해야 길이 차이로 경계를 믿을 수 있음.

실무 팁 :  
max_length는 실제 길이 분포(최대, 상위 1%) + 여유로 정해야 함.배치는 가장 긴 것에 맞춰 패딩. 긴 문서는 학습 데이터에서 다르기보다 RAG 단계에서 필요한 부분만 넣도록 줄임.


### 품질 검사 : 조건과 근거 부족 사례
- 가중치를 바꾸기 전에 자료부터 확인. 학습이 끝난 뒤에 데이터 오류를 찾으면 시간과 비용이 큼.
- 검사 함수(validate_record)는 앞 단계부터 차례로 레코드를 검사하고, 틀리면 AsserttionError로 거절.
- 검사 함수도 코드이므로 버그가 있을 수 있음. 그래서 일부터 틀린 자료로 검사 함수 자체를 시험.

PPT 예시 : validate_record 다섯 단계
1. 식별 정보 : 필드 4개, group_id와 case_type이 명세와 같음
2. 대화 : 역할 순서, system == SYSTEM_PROMPT, user == 명세
3. 응답 형식 : status, answer, citations 3필드
4. 인용 : 제공 문서 ID의 부분집합, 중복 없음
5. 업무 규칙 : 초과, 이하, 보류 문구

### 그룹 단위로 나누기
개념 : 무엇이 같으면 같은 문제인가를 정하고, 그 단위로 나눈다.
- 행을 무작정 섞어서 나누면, 같은 문제의 "형제"가 train과 test에 갈라져서 모델이 시험 문제를 이미 본 셈이 됨. 이것이 데이터 누수이고, 점수가 부풀음.
- 그래서 "같은 문제"의 단위를 저해서 그 단위째로 나눔.

train, dev, tset는 "언제 보느냐"로 구분.
| |용도|주의|
|---|---|---|
|train|가중치 갱신|여 점수가 좋은 건 당연|
|dev|점검/비교|여러 번 봐서 부풀음|
|test|후보/설정을 고정한 뒤 마지막에 한 번|보고 고치면 dev가 됨|

데이터에도 버전과 지문을 남겨야함.

- JSONL은 한 줄에 레코드 하나라서 줄 수 = 레코드 수이고, 한 줄씩 읽고 쓰기 쉬움.
- dataset_info.json은 데이터 카드로, 합성 여부, 모델과 revision, system_prompt, 분할 seed롸 그룹, 길이, 파일 해시, 한계를 담음
- 실험 기록에 모델 버전과 데이터 해시를 함께 남김
