### SFT, DPO, LoRA, QLoRA를 고르는 흐름
|단계|고르는 질문|선택지|
|---|---|---|
|문제 진단|파인튜닝이 필요한 문제인가?|프롬프트, RAG, 파인튜닝|
|학습 목표|무엇을 정답 신호로 쓰나?|SFT, DPO|
|학습 대상|어떤 파라미터를 학습하나?|전체, LoRA, QLoRA|
|모델 크기|어떤 크기의 모델에서 시작하나?|작은 모델, 큰 모델|

### 평가(evalation)의 기본 원칙
평가 전에 같은 시험지를 본 결과인지 확인
- 서로 다른 실행의 결과를 비교하려면, 각 결과가 같은 데이터/같은 모델 파일에서 나왔늕 먼저 맞춰야함. 다른 데이터로 낸 결과를 섞으면 비교 자체가 무의미해짐  

파일 지문
- 파일 내용에서 계산한 고정 길이의 지문. 파일이 1바이트만 달라도 완전히 다른 값이 나오기 때문에, 지문이 같으면 같은 파일이라고 확신할 수 있음.
- 보고서에 입력 파일의 지문을 기록해 두고, 평가할 때 지금 파일의 지문과 대조해서 출처를 확인
- 같은 내용이라도 다시 압축하면 지문이 달라질 수 있음. ZIP 안에 파일 수정 시각 같은 메타데이터가 들어가기 때문

dev와 test를 쓰는 시점
- dev : 후보를 비교하고 고를 때 반복해서 보는 데이터
- test : 후보를 고정한 뒤 마지막에 한 번 여는 데이터. dev에서 후보를 고르는 동안에는 열지 않음.

응답을 채점하는 세 가지 층
|층|묻는 것|누가|한계|
|---|---|---|---|
|형식 검사|프로그램이 읽을 수 있나|자동(코드)|내용의 옳고 그름은 못 봄|
|업무 의미|일이 맞게 처리됐나|사람이 원문을 읽음|비용이 큼|
|참조 일치|모범답안과 글자까지 같나|자동 가능|가장 좁은 기준, 표현만 다른 맞는 답도 불일치|
- 이 세 값을 하나의 정답률로 섞지 않음.


형식 검사의 세 관문
- 앞 관문에서 떨어지면 뒤 관문은 검사하지 않고 False로 둠. 그래서 실패는 첫 번째로 떨어진 관문 하나로 셈.  

|관문|확인하는 것|이런 답이 걸림|
|---|---|---|
|json_object|JSON 객체로 읽히나|코드 펜스로 감싼 JSON, 앞뒤에 설명이 붙은 답|
|schema_ok|필수 키, 값의 타입, 상태와 인용의 관계가 맞나|보류인데 answer가 빈칸, 키 누락|
|citation_ids_ok|인용한 ID가 제공한 문서의 ID 안인가|없는 문서 ID를 인용, ID를 번역해 버림|

형식이 완벽한 오답도 통과함
- 세 과문이 모두 True여도 답은 틀릴 수 있음
- 숫자의 대소 관계, 승인 시점, 근거가 부족한 이유 같은 의미는 형식 검사가 못 봄. 그래서 의미는 사람이 원문을 읽어서 확인함

### 같은 입력으로 응답 변화 비교하기
공정한 비교의 조건  
같게 맞출 것/안 맞춘 것을 구분
- 같게 맞춘 것 : 문항, 질문, 근거 문서, 생성 설정
- 다른 것 : 학습 목정(SFT,DPO), 양자화 여부, 학습에 쓴 자원
- 그래서 "같은 입력으로 비교했다"는 같은 환경, 같은 학습 조건이라는 뜻이 아님

문항을 순서가 아니라 IDㄹ 맞춘다
- 결과 파일의 줄 순서가 달라도 같은 문제끼리 비교되도록 case_id로 정렬
- ID가 같아도 질문이나 근거 문서가 다르면 비교를 멈춤. 생성 설정(greedy, 최대 토큰 등)도 같은지 확인. 입력이 조금이라도 다르면 결과 차이의 원인을 알 수 없기 때문

저장된 응답을 다시 채점
- 이미 저장해 둔 응답을 같은 기준으로 재채점. 모델을 다시 올려서 생성하면 시간이 들고, 생성이 달라져 비교 대상이 바뀔 수도 있음

학습 시간과 메모리는 합쳐서 순위를 매기지 않음
- 각 실행이 잰 구간과 환경이 달라서, 하나의 종합 순위로 합치면 오해가 생김. 품질 비교와 자원 비교는 따로 읽음  

비교하는 방법 다섯 가지 의미
|이름|출발점 -> 학습|
|---|---|
|base|공개 모델 그대로(학습 전)|
|full_sft|공개 모델 -> 전체 가중치 SFT|
|lora|공개 모델 -> LoRA(A*B만)|
|qlora|4비트 기반 -> LoRA(A*B만)|
|dpo| SFT결과 -> 선호 학습|

### 검색과 API에 학습 모델 연결하기
요청 한 건이 지나가는 네 칸
|칸|하는 일|
|---|---|
|입력 검사|잘못된 요청은 접수 거절 (422)|
|검색|질문에 맞는 문서를 찾음|
|생성|문서를 읽고 답을 만듦(학습한 모델)|
|출력 검사|답의 형식을 확인(200/502)|

검색  
- corpus : 검색 대상 문서 모음
- 키워드 검색 : 질문과 문서에 같은 낱말이 얼마나 겹치는지로 점수를 매기는 단순한 방식
- 벡터 검색 : 문장을 숫자 백터로 바꿔 뜻이 비슷한지로 찾는 방식 (동의어에 강함)

키워드 검색의 한계  
- 동의어를 못 찾음
- 다른 주제인데 낱말이 겹치면 잘못 찾음
- 문서를 못 찾으면 빈 목록이 됨

API와 요청/응답 계약
API
- 정해진 양식으로 요청을 넣으면 정해진 양시으로 답이 나오는 창구

FASTAPI
- PAI 서버를 만ㄷ는 파이썬 프레임워크

Pydantic
- 요청 데이터의 형식과 제약을 선언하고 검사하는 도구

HTTP 상태 코드
|코드|일반적 의미|이 구조에서 쓰는 뜻|
|---|---|---|
|200|성공|모델 답의 형식이 맞음|
|422|요청 내용이 처리 불가|사용자가 보낸 요청이 잘못됨|
|502|중간 서버가 상대 서버에게서 잘못된 응답을 받음|모델이 낸 답의 형식이 잘못됨 (답이 잘린 경우 포함)|

### 실패와 수정 방향
|실패|알아보는 법|수정 방향|
|---|---|---|
|형식|첫 실패 단계|학습 성정, 데이터 형식|
|검색|검색된 문서 목록|동의어, 검색 방법, 검색 평가|
|업무 판단|문서는 맞는데 answer가 틀림|비교 사례, 규칙 코드, 사람 검토|
|운영|이 구조로는 알 수 없음|인증, 동시 요청, 외부 공개 등 목적에 맞는 별도 시험|
