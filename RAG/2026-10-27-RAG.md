## 배운 내용
문서 ID : 검색이 근거를 찾았는지 비교하는 용도  
원문 문장 : 답변의 금액, 단위, 조건을 검토하는 용도  
청크 크기를 바꾸면 chunk_id는 바뀌어도 document_id는 유지되므로, 근거를 문서 ID로 적으면 청킹을 바꿔도 같은 기준표를 재사용할 수 있음  

답이 없는 질문 : '정보 없음'을 '아니다'로 바꾸지 않는 것이 핵심

JSONL은 json.loads에 통째로 넣으면 Extra data 오류가 나므로 splitlines()로 줄마다 읽음  

Hit@k : 하나라도 찾았으면 1  
Recall@k : 필요한 문서 중 찾은 비율  

ex)  
|k|찾은 문서|Hit@k|Recall@k|
|---|---|---|---|
|1|meal|1|0.5|
|3|meal, travel|1|1.0|
|5|meal, meeting, travel, vpn|1|1.0|

Hit만 보면 놓치는 것 : k=1은 Hit이 1이지만 숙박비 근거가 없음. Recall의 분모는 검색 결과 수가 아니라 필요한 문서 수  
Recall의 한계 : k=5에서 무관한 eeting, vpn이 섞여도 Recall은 안내려감. 잡음은 알려 주지 않으므로 Context 길이와 처리 시간, 최종 답변 정확성도 함께 봄  

RAGAS : RAG 시스템의 품질을 자동으로 채점해주는 오픈소스 평가 라이브러리. 사람이 일일이 답변을 읽고 채점하는 대신, 질문, 검색된 Context, 답변을 넣으면 지표별 (0~1)를 계산해 줌  

RAGAS가 필요한 이유 : RAG는 검색과 생성 두 단계로 이루어져 있어서, 답이 틀렸을 때 어느 단계 문제인지를 알아야 고칠 수 있음.

RAGAS 지표  
|지표|비교하는 것|묻는 질문|
|---|---|---|
|Faithfulness|답변 <-> Context|답변의 주장이 근거로 뒷받침하나(환각 확인)|
|Answer Relevancy|답변 <-> 질문|갑변이 질문과 관련된 내용인가|
|Context Precision|Context 순서 <-> 참고 답변|쓸모있는 근거가 앞쪽에 있나|
|Context Recall|참고 답변 <-> Context|참고 답변의 사실이 Context에 다 들어 있나|


### RAG 문제 별 해결 방안  
|실패|해결|
|---|---|
|문맥이 중간에 잘림|Parant-Child, Context 압축|
|검색이 실패함|재검색(Corrective/Agentic RAG)|
|여러 문서의 관계를 따라가야 함|GraphRAG|
|표, 이미지 속에 답이 있음|Multimadal RAG, ColPali|

Parant-Child와 Context 압축 : 검색을 Child로 그 Child가 속한 Parant를 넘김. Parant는 새로 임베딩하지 않고 document_id로 원문을 조회  
Context 압축 : 한도, 초과, 승인, 영수증이 든 문장만 고르는 단어 기반 추출. 추출은 원문 표현을 유지하지만, LLM 요약은 더 짧아지는 대신 조건이 바뀔 수 있음.  

Corrective RAG와 Agentic RAG : 한 번 검색하고 끝인 기본 RAG에 '결과를 보고 판단해서 다시 시도하는 단계'를 더한 방식. 검색이 잘 됐는지 확인하고 아니면 보정  
|접근|추가하는 판단|수업 범위|
|---|---|---|
|기본 RAG|정해진 검색 후 생성|한번 검색 흐름|
|Agentic RAG|다음 질의, 도구, 종료 선택|최대 두 번의 사내 검색|
|CRAG|검색 결과 품질 평가 후 보정|근거 검토 후 재검색하는 발상|
|Self-RAG|검색 필요성과 생성을 모델이 비평|학습된 비평 토큰, 연구 구조 소개|

CRAG : 검색 결과가 관련있는지 평가하고, 부족하면 쿼리를 고치거나 웹 같은 외부 검색으로 보완  
Agentic RAG : LLM이 "에이전트"처럼 행동을 고름(답변할지, 다시 검색할지, 포기할지)  
Self-RAG : 일반 LLM에게 "검토해 봐"라고 시키는것과는 다름, 비평용 특수 토큰을 학습시킨 모델을 씀  

GraphRAG : 문서를 "청크 조각"이 아니라 "개체(사람, 규정, 항목 등)와 그 관계로 이루어진 그래프"로 정리해서 검색에 쓰는 RAG 방식. 기본 RAG가 질문과 비슷한 텍스트 조각을 찾는다면, GraphRAG는 개체들이 어떻게 연결되어 있는지를 따라가며 답을 찾음.  

장점 : 전체 문서를 아우르는 요약형 질문에 강함  
단점 : 비용과 시간이 많이 듬  

Multimodal RAG와 ColPali  

Multimodal RAg : 텍스트뿐 아니라 이미지(표, 차트 ,스캔 문서, 슬라이드 등)까지 검색 근거로 쓰는 RAG  
ColPali : 문서 페이지를 이미지 그대로 읽어서 검색하는 모델  
쓰는 이유 : 실제 문서는 순수 텍스트가 아님. PDF나 스캔본에는 표, 차트, 도식 등이 있고, 이걸 텍스트로 뽑는 과정에서 정보가 깨지기 쉬움.
