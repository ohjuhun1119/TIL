## 배운 내용
### Few-shot : 모델이 무엇을 해야 하는지 알려 주는 기법
프롬포트 안에 입력과 출력 예시를 몇 개 넣어서, 모델이 그 패턴을 따라 하도록 하는 방식
- 출력 형식을 정확히 맞춰야 할 때 : JSON 구조, 특정 라벨 체계, 정해진 문장 톤
- 작업 정의가 애매할 때 : 경계 사례를 어떻게 처리할지 예시로 기준을 잡아줄 수 있음
- 도메인 특화 작업일 때 : 금융 상담 분류처럼 모델이 기본적으로 잘 모르는 라벨이나 용어를 쓰는 경우
- 파인튜닝 없이 빠르게 성능을 올리고 싶을 때 : 데이터가 적거나 학습 비용을 쓰기 어려운 상황에서
- 주의할 점 : 예시의 순서와 라벨 분포에 결과가 민감하게 반응하고, 예시가 길어지면 토큰 비용이 늘어남

### Self-Consistency : 모델이 낸 답을 더 믿을 만하게 만드는 기법
같은 질문에 대해 temperature를 0보다 크게 두고 Chain-of-Thought 추론을 여러 번 샘플링  
그 다음 최종 답 가운데 가장 많이 나온 것을 다수결로 고름 / 추론 경로는 여러 가지여도 정답은 하나로 수렴
- 정답이 하나로 정해지는 추론 문데 : 수학, 논리 퍼즐, QA처럼 답을 비교하고 집계할 때
- 한 번의 CoT 결과가 들쭉날쭉할 때 : 추론 중간에 실수가 섞여 답이 흔들리는 경우, 여러 경로를 모으면 우연한 오류가 상쇄
- 비용이나 지연보다 정확도가 중요할 때 : 호출 횟수가 N배로 늘어나기 때문
- 주의할 점 : 요약, 글쓰기 같이 정답이 하나로 정해지지 않는 작업에는 맞지 않음  

** Chain-of-thought : 모델이 최종 답을 바로 내지 않고, 중간 추론 과정을 단계별로 글로 풀어 쓴 다음 답에 도달하게 하는 프롬프팅 기법

| |Few-shot|Self-Consistency|
|---|---|---|
|해결하려는 문제|작업 이해, 형식 맞추기|추론 결과의 불안전성|
|적용 위치|프롬포트(입력)|디코딩과 후처리(출력)|
|비용|프롬포트 길이 증가|호출 횟수 N배|
|적합한 작업|분류, 추출, 형식 변환|수학, 논리, 다단계 추론|

### Reasoning : 모델이 답하기 전에 중간 추론 과정을 거치게 하는 것
쓰는 이유  
- 여러 단계를 거쳐야 하는 문제의 정확도가 올라감 : 수학, 논리, 조건이 많은 질문처럼 답을 한 번에 낼 수 없는 문제에서 효과가 큼 / 중간 겨로가를 글로 적어 두고 그다음 단계를 이어 나감
- 연산을 늘려서 성능을 살 수 있음 : 모델 크기를 키우거나 다시 학습하지 않아도, 추론할 때 토큰을 더 스게 하면 성능이 올라감 / 어려운 문제에만 더 많이 생각하게 하는 방식으로 비용을 선택할 수 있음
- 스스로 검토하고 고칠 기회가 생김 : 추론 모델은 앞 단계를 다시 확인하거나, 막히면 다른 접근으로 돌아가는 행동을 보이기도 함

한계  
- 비용과 지연이 커짐 : 생성하는 토큰이 많아지는 만큼 비용이 늘고 응답이 느려짐
- 없늦 지식을 만들어 주지는 않음 : 이미 가진 정보를 잘 조합하게 도와줄 뿐이지 모르는 사실이나 최신 정보는 생기지 않음. RAG나 검색처럼 외부 정보를 넣어 주는 방법이 필요
- 그럴듯하게 틀릴 수 있음 : 초반 단계에서 실수하면 그 뒤의 추론이 그 실수 위에 쌓임

답에 이르기까지 단계가 많고, 정확도가 비용보다 중요하며, 필요한 저옵가 이미 입력이나 모델 안에 있는 경우에 Reasoning을 쓰는 것이 좋음. 반대로 단순하고 빠른 응답이 피요한 작업이나 외부 지식이 부족한 작업이라면, Few-shot이나 검색 결합을 먼저 고려

enum : enumeration(열거)의 줄임말로 '이 필드에는 나열한 값 중 하나만 들어올 수 있다'는 JSON Schema 키워드

properties : JSON Schema의 표준 키워드 (객체 안에 어떤 키들이 있고, 각 키의 값은 어떤 모양인지)
