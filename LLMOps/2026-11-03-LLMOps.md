### 배운 내용
SLI : 서비스 상태를 측정하는 지표 / 요청 완료율, 응답 지연 시간, 오류율, 답변 품질, 토큰 사용량  
SLO : SLI에 대해 정한 목표  

지표를 만들 때는 이름만 붙이지 말고 무엇을 한 건으로 셀지, 어떤 요청을 포함할지, 어느 기간을 볼지 정해야 함.  
에어전트 요청 한 건 안에 모델 호출이 여러 번 있을 수 있기 때문  

## 지표 정의와 누락값 처리
지표
- 품질 : 업무에 맞고 정확한 답을 했는가
- 지연 : 사용자가 얼마나 기다렸는가
- 오류율 : 요청을 처리하지 못한 비율은 얼마인가
- 토큰/비용 : 모델 사용에 자원을 얼마나 썼는가  

요청은 완료/실패/미확인으로 구분  

미확인 : 수집 지연, 취소, timeout, 기록 누락 등으로 최종 상태를 아직 모르거나 판단하기 어려운 경우  

미확인을 성공이나 실패로 임의 분류하면 실제 상태를 왜곡함. 원인을 모르는 상태는 미확인으로 남겨 원인을 확인하는 것이 맞음  

느린 요청들이 timeout으로 끝나 지연 측정 대상에서 빠지면 완료된 요청들만 계산한 지연은 낮아짐. 그래서 지연 시간만 보지 말고 완료율과 오류/미확인 건수도 함께 확인해야 함.  

p50와 p95  
지연 시간의 분포를 간단히 보는 대표 값.
- p50 : 요청 절반이 이 시간 안에 끝남. 중앙값에 해당함
- p95 : 요청 95%가 이 시간 안에 끝남. 느린 요청이 얼마나 오래 걸리는지 살피는 데 유용함.  

None != 0  
측정값이 실제로 0이라면 0으로 기록하고, 아직 알 수 없으면 None으로 남겨야 함.  
- 비용 0 : 실제로 비용이 0이라고 확인됨  
- 비용 None : 비용을 아직 확인하지 못함  
- 지연 None : 완료 지연을 측정할 수 없음  
확인된 비용만 합한 값과 전체 요청의 확정 비용은 구분해야 함. 일부 요청의 비용을 모르면 확정 총액은 미확인으로 두고, 비용을 확인한 요청의 비율도 함께 보여줌.  

## 토큰과 지연을 실제 요청에서 측정하기
후보 개선안의 효과를 보려면 같은 질문을 기준 버전과 후보 버전에 각각 실행하고, 바뀐 조건을 하나로 제한해야 함.  

문맥을 줄였을 때 입력 토큰은 줄었지만, 지연은 토큰 수만큼 비례해 줄지 않았음. 모델 서버 상태, 캐시, 답변 생성 시간 등 다른 요소도 영향을 주기 때문.  

토큰 사용량 : 모델이 실제로 보고한 사용량을 사용  
요청 지연 : 검색과 입력 구성, 모델 호출 시간을 포함  
모델 생성 시간 : Langfuse 화면의 호출 구간처럼 모델 생성 자체의 시간  

질문 두 개를 버전별로 한 번씩 실행한 결과는 효과를 탐색하는 단서이지, 운영 성능이 개선됐다는 증명은 아님.  
운영 적용 전에는 더 많은 재표 질문을 같은 조건에서 반복하고, 토큰뿐 아니라 답변 내용, 출처, 오류, 지연 분포를 같이 배교해야 함.  


## 오류율과 사용자 피드백 해석
기술적으로 성공한 응답이 사요자를 만족시켰다는 뜻은 아님. API 호출은 성공했어도 답변이 틀렸거나, 출처가 부정확하거나, 설명이 너무 길 수 있음.  
- 기술적 오류율 : 요청이 실행을 완료하지 못한 비율
- 사용자 피드백 : 실행 결과가 업무에 도움이 됐는지에 대한 평가  

응답률과 긍정 비율은 분모가 다름
- 피드백 응답률 : 피드백을 받은 Trace 수 / 전체 요청 수
- 응답자 중 긍정 비율 : 긍정 피드백 수 / 전체 피드백 수
피드백이 없는 요청은 긍정이 아닌 평가를 받지 않은 상태.  
미응답을 긍정으로 취급하면 만족도가 부풀려짐. 긍정이 아닌 미확인으로   

낮은 점수는 개선 데이터가 될 수 있음.  
낮은 피드백이 달린 Trace를 열어 원인을 분류하고, 실패 사례를 평가 데이터셋에 넣으면 다음 변경을 검증할 수 있음.
1. 낮은 평가의 Trace를 연다.
2. 내용, 출처, 지연, 말투 등 원인을 분류
3. 개인정보를 제거하거나 익명화
4. 사례를 dev 평가 데이터에 추가
5. 새 변경안을 같은 사례로 회귀 검사
원문 피드백을 그대로 복사하기보다 필요한 내용을 정리하고 민감 정보를 제거해야함.

## 지표를 바탕으로 개선 판단과 대응하기
집계 숫자만 보지 말고, 같은 질문을 기준 버전과 후보 버전에서 비교한 다음 개별 Trace까지 내려가 확인해야 함. 요청 수, 토큰, 지연, 답변, 사용한 근거를 나란히 보면 어디서 차이가 났는지 알기 쉬움.  

비용은 중복 합산하지 않기  
한 요청의 Trace에는 요청 전체를 나타내는 부모 구간과 개별 모델 호출을 나타내는 자식 구간이 있을 수 있음. 부모 비용과 자식 모델 비용을 모두 더하면 같은 비용을 중복으로 셀 수 있음. 실제 모델 호출인 GENERATION 구간의 비용을 모으도록 안내.  

경보 발생 시 확인 순서
1. 요청 수와 미확인 비율로 영향 범위를 삺핌
2. 기능/환경/버전 중 어디에서 발생했는지 좁힘
3. 최근 변겨오가 실패 Trace를 대조
4. 필요하면 검증된 구성으로 완화하거나 복원
5. 같은 평가 사례로 다시 확인

기억해야 할 것
- 지표를 보기 전에 측정 단위/분모/기간을 정함
- 미확인과 0은 다름. 누락값을 임의로 성공/실패/무료로 바꾸지 않음
- p95 지연이 낮아져도 완료율이 악화됐다면 장애일 수 있음
- 토큰 감소만으로 개선을 단정하지 말고 답변 품질/출처/오류/지연을 함께 비교
- API 성공은 사용자 만족을 보장하지 않음
- 피드백을 Trace에 연결하고, 응답률과 긍정 비율의 분모를 구분
- 작은 표본이나 불안전한 비용 정보로는 개선을 확정하지 말고 검토 상태로 둠
- 경보가 나면 집계에서 개별 Trace로 내려가 원인을 확인하고, 검증된 구성으로 복원한 뒤 재검증
